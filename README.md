> Frameworks and visual tools for agent coordination, durable workflows, and human approvals.

45 projects · Upstream documentation checked 2026-09-30. Curated by [agentlist.io](https://www.agentlist.io).

**Move from one agent to coordinated work.**

Start with the coordination problem: separate independent tasks, pass work between specialists, or keep a long-running workflow recoverable. Adding agents also adds state, handoffs, and failure cases. Choose the smallest coordination model that makes those responsibilities clear.

Tools that compose agent steps, delegate work, or manage multi-agent workflows. Coding-agent clients and model-routing gateways are separate categories. Frameworks require application code; visual builders provide an authoring interface.

## How to choose

- Works with: Can it use your agents and tools directly, or does it require rewriting them in its own framework?
- Runs where: Who operates the workers, queues, scheduler, and persistent state? Which parts require a hosted service?
- Needs access to: How are tools, credentials, and workspaces assigned to individual agents? Can concurrent workers change the same files?
- Keeps what: Are task state, decisions, artifacts, and handoffs durable? Can failed work resume without repeating completed actions?
- Human involvement: Where can you approve a plan, redirect a worker, inspect a diff, or stop the whole workflow?
- Main limitation: How does it handle conflicting edits, failed handoffs, retries, and duplicate work? Distinguish documented guarantees from examples.

Use these questions to narrow your shortlist. An entry’s source link records the documentation used for its description; it does not mean every question above has been answered or tested. Treat undocumented capabilities as unknown, and confirm requirements against the linked project before adopting it.

## Code-first frameworks

- [Agno](https://github.com/agno-agi/agno) - Python framework and AgentOS runtime for agents, teams, and workflows. You define agents in the SDK, serve them as an API, and manage runs in the AgentOS UI; starter templates use Docker and store sessions, memory, and traces in a database you operate, and the linked docs describe pausing a run for confirmation and blocking tools that need approval. A telemetry event is sent per run unless AGNO_TELEMETRY is false, and the README says that event omits prompts and outputs. **Python framework.**
- [CrewAI](https://github.com/crewAIInc/crewAI) - Python framework for role-based crews and event-driven flows, running in your process against the model provider you configure. Agents and tasks can be declared in JSON or Python, the README points to human input during a run plus checkpointing as the flow grows, and CrewAI AMP is a separate commercial control plane rather than part of the open-source process. The README does not describe how two agents should resolve conflicting edits to the same files. **Python framework.**
- [Google ADK](https://github.com/google/adk-python) - Code-first Python toolkit for agents and graph workflows, including routing, loops, retries, and a tool-confirmation step before a guarded tool runs. The README says it is optimized for Gemini but not tied to one model, that adk web is a local dev UI, and that Cloud Run or Vertex AI Agent Engine are documented deploy targets; sibling SDKs google/adk-go and google/adk-js are the Go and TypeScript kits and are not separate rows. An export format apart from the app you deploy is not documented in the README. **Python SDK.**
- [LangGraph](https://github.com/langchain-ai/langgraph) - Low-level Python library for long-running stateful workflows; the README points to LangGraph.js as the JavaScript library, which is not a separate row, and says the Python library can be used without LangChain. Linked docs describe persisting a run so it can resume after a failure, and letting a person inspect and edit state at an interrupt, while LangSmith remains a separate tracing and deployment product. The README does not itself specify how two workers should merge conflicting file edits. **Python library.**
- [Mastra](https://github.com/mastra-ai/mastra) - TypeScript framework for agents and graph workflows that you embed in a Node app or run as its own server, with a local Studio UI for trying agents, workflows, and tools. Linked docs say storage keeps a suspended run so a person can approve or supply input before it resumes, and model calls use the provider credentials you configure. The README does not require a hosted Mastra service to define or run a workflow. **TypeScript framework.**
- [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) - Python and .NET framework for agents and graph workflows, including sequential, concurrent, handoff, and group patterns, with checkpointing and human-in-the-loop control documented in the README. It points to microsoft/agent-framework-go for the Go SDK rather than a third row here, and samples show Microsoft Foundry and other providers inside an app you run. AutoGen and Semantic Kernel READMEs direct new users here; those older repositories are listed separately because they say they are no longer the starting point. **Python and .NET.**
- [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) - Python SDK for agents, tools, guardrails, sessions, and handoffs, with openai/openai-agents-js named in the README as the JavaScript library and not given a separate row. Runs execute in your process, with optional sandbox agents, an optional Redis extra for sessions, and documented human-in-the-loop checks, and the README says the SDK can call OpenAI APIs or many other chat models. It is not a visual builder. **Python SDK.**
- [Pydantic AI](https://github.com/pydantic/pydantic-ai) - Typed Python agent loop for tools and structured output, callable from a script, a terminal, or a voice session. The README documents human-in-the-loop tool approval and optional durable execution, including Temporal, so model and tool calls can be replayed after a restart when you attach that capability; Pydantic Graph and Pydantic Evals are separate packages. Logfire and the model gateway are optional products, and a local agent run does not require them. **Python framework.**
- [smolagents](https://github.com/huggingface/smolagents) - Small Python library whose CodeAgent writes actions as Python code, next to a ToolCallingAgent that uses ordinary tool calls, with multi-agent hierarchies documented in the README. Code can run in Blaxel, E2B, Modal, or Docker sandboxes, which this list did not test, and you pick the model, including a local transformers or Ollama model or a hosted API. The README documents pushing an agent to the Hugging Face Hub and does not document a required human approval step before code runs. **Python library.**
- [CAMEL](https://github.com/camel-ai/camel) - Python research framework for multi-agent role play, agent societies, and tool-using chat agents. The quickstart runs in your process with a model API key and keeps agent memory across steps, and a cookbook linked from the README covers human oversight and tool approval. Orchestration is one research use, alongside data generation and simulated environments, and the ChatAgent quickstart does not document a durable checkpoint store. **Python framework.**
- [AG2](https://github.com/ag2ai/ag2) - Python framework, Apache-2.0, for agents that cooperate over a Network of a hub, typed channels, and a write-ahead log, with a documented pause so a person can confirm or supply missing information. AG2 v1 is not the classic autogen import; that code is the separate ag2ai/ag2-classic repository, which the README says remains maintained. AG2 is a community continuation of AutoGen's ideas, not Microsoft Agent Framework, and it does not replace Agent Framework. **Python framework.**
- [Haystack](https://github.com/deepset-ai/haystack) - Python framework for retrieval pipelines and, separately, agent workflows; orchestration is one use, not the whole project, because the README also centers retrieval, routing, memory, and generation for search and RAG. Components run in your process, and the README points to Hayhooks when you want to expose a pipeline over HTTP or MCP. A required human approval step is not described in the README, and you bring the model and the document stores. **Python framework.**
- [Swarms](https://github.com/kyegomez/swarms) - Python library for composing agents into sequential, concurrent, hierarchical, and group-chat workflows. An agent is a model plus tools and memory, runs in your Python process, can call MCP servers by URL, and uses WORKSPACE_DIR as the documented workspace path. The first-agent example does not describe a required human approval gate, and the README does not give a merge rule for conflicting edits across agents. **Python framework.**
- [Agency Swarm](https://github.com/VRSEN/agency-swarm) - Python framework that builds multi-agent agencies on top of the OpenAI Agents SDK, with roles, tools, and communication only along flows you declare through a send_message tool. The README says other model vendors can be reached through LiteLLM, and that you persist threads with your own load and save callbacks. A person-approval step is not documented in the README, and this layer does not replace the Agents SDK. **Python framework.**
- [VoltAgent](https://github.com/VoltAgent/voltagent) - TypeScript framework for typed agents, tools, MCP, and declarative multi-step workflows. The README's expense example suspends until a person submits a decision and then resumes, memory can use an adapter such as a local LibSQL file, and the dev server links to the VoltOps console for trying the agent. That console is a separate observability and deploy surface, cloud or self-hosted, and is not required to define the agent in code. **TypeScript framework.**
- [AX](https://github.com/google/ax) - Declarative orchestrator for agent tasks on Kubernetes, not a library you import into an app. The README says you apply Task and Workspace manifests, Agent Substrate sandboxes each task with CPU and memory limits, and ax suspend and ax resume pause and continue an idle task; this list did not test that sandbox boundary, and you need a cluster running Substrate plus the gRPC CLI. The README warns the API may break before a stable release, and ax ssh is the documented way to look inside a running sandbox. **Kubernetes orchestrator.**
- [Strands Agents](https://github.com/strands-agents/harness-sdk) - Python and TypeScript SDK for an agent loop that runs in your process, which the README says does not add a hosted control plane. A harness package builds a preassembled agent, and the lower-level SDK is where you attach tools, providers, sessions, hooks, MCP, and multi-agent patterns, with documented support for Amazon Bedrock, Anthropic, OpenAI, and Gemini. Hooks can intercept a step, and the README does not require a separate approval service. **Python and TypeScript.**
- [MetaGPT](https://github.com/FoundationAgents/MetaGPT) - Python framework that turns a one-line requirement into a software workspace by walking role steps such as product, architecture, and engineering, writing a repository under ./workspace from model settings in ~/.metagpt/config2.yaml. That quickstart does not document a human approval stop before the write. The repository is not archived, and the last push in this snapshot was 2026-01-21, so it is quiet rather than described here as unmaintained. **Python framework.**
- [PraisonAI](https://github.com/MervinPraison/PraisonAI) - Python library for agents, handoffs, and AgentFlow graphs with route, parallel, and repeat steps. The README shows an approval flag as a human gate before a risky tool runs, memory that persists when you pass a user id, and optional execution in a shared Docker sandbox or a hosted agent runtime instead of only on your machine. The README does not document how two agents should merge conflicting edits. **Python framework.**
- [Claude Agent SDK](https://github.com/anthropics/claude-agent-sdk-python) - Python SDK that programs Claude Code's agent loop, not a general multi-vendor orchestrator. The README says the Claude Code CLI is bundled with the package and used by default, with an option to point at another CLI path, and permissions stay with Claude Code: allowed_tools auto-approves listed tools and does not remove the rest, while other tools follow permission_mode or a can_use_tool callback. Custom tools are in-process MCP servers, and the README does not show this SDK switching among unrelated agent products. **Python SDK.**
- [Agent Squad](https://github.com/2FastLabs/agent-squad) - Library that routes each user turn to one registered agent, with Python, TypeScript, and on-device Swift runtimes; a classifier chooses from descriptions and history, the orchestrator stores the exchange, and a supervisor can call other agents as tools. Python and TypeScript are described as running on a laptop, in containers, or on Lambda, Swift stays on Apple devices, and the README says the project moved from awslabs/agent-squad. The basic route path does not document a human approval step. **Multi-runtime library.**
- [Griptape](https://github.com/griptape-ai/griptape) - Python framework that structures work as a single-task agent, a pipeline of tasks, or a workflow of parallel tasks, with swappable drivers so the model provider can change without rewriting the graph. The README distinguishes conversation memory from task memory that keeps large outputs off the prompt, and runs happen in your Python process. It points to Griptape Nodes as a separate visual desktop app, which is not its own row, and it does not describe a required human approval step. **Python framework.**
- [mcp-agent](https://github.com/lastmile-ai/mcp-agent) - Python framework that connects agents to Model Context Protocol servers and composes a small set of workflow patterns. The README says the same agent code can run on asyncio or on Temporal so a workflow can pause and resume without an API change, lists signals for human input, and expects API keys in a secrets file or the environment. The repository is not archived, but the last push in this snapshot was 2026-01-25, so it is quiet rather than abandoned. **Python framework.**
- [ChatDev](https://github.com/OpenBMB/ChatDev) - ChatDev 2.0, also called DevAll, is a multi-agent platform with a visual canvas and a Python package that runs YAML workflows. The README says you define agents and flows in configuration, launch them from the local FastAPI and Vue UI or from code, can give human feedback while a run is open, and writes generated files under WareHouse. The older virtual-software-company mode stays on the chatdev1.0 branch and is not the default product in this README. **Workflow platform.**
- [uAgents](https://github.com/fetchai/uAgents) - Python library for agents that message each other on the Fetch.ai network. The README says each named agent registers on the Almanac smart contract at startup, keeps a private key in a local file when you do not pass a seed, and can run scheduled tasks or handle incoming messages. That is coordination by messages between agents you write, and the quickstart does not document a human approval step or an offline mode that skips Almanac registration. **Python library.**
- [LightAgent](https://github.com/wanxingai/LightAgent) - Python framework for one tool-using agent, LightSwarm delegation, and LightFlow graphs. The README describes LightFlow as a DAG with retries, checkpoints, resume, and approval nodes, documents a human-approval hook for selected tools and handoffs, and uses OpenAI-compatible endpoints with MCP over stdio and SSE. Durable sessions are optional, and the README says arbitrary Python execution is opt-in and needs an explicit sandbox boundary, which this list did not test. **Python framework.**
- [Zeroshot](https://github.com/the-open-engine/zeroshot) - Native program that turns a software goal into a fixed agent graph: one worker implements, separate agents review, and failures return to a bounded repair step. The README says the graph, not a runtime agent, chooses the next step, every event is written to a SQLite ledger, local runs reuse a Codex or Claude Code login, and delivery to a branch or pull request is optional. The zeroshot ui inspects runs in a browser, and a human gate distinct from those agent reviewers is not documented as required for a local run. **Native graph runner.**
- [Astron Agent](https://github.com/iflytek/astron-agent) - Self-hosted platform for agent workflows, model access, MCP tools, and RPA steps, rather than a small library you import. The README's quick start is Docker Compose, with Helm as the other documented install, and it also links a hosted console at agent.xfyun.cn, so execution is the services you deploy. A human approval step is not documented in the README, and the quick start does not describe exporting a workflow as a standalone function call. **Workflow platform.**
- [Octop](https://github.com/TencentCloud/Octop) - Self-hosted Python assistant for more than one person, serving a web dashboard, a CLI, and chat-channel gateways from one process. The README says you switch specialist experts per task, labels AgentTeams as a beta coordinator for multi-step work, documents tool approval before some actions, and stores control-plane data in SQLite under ~/.octop/ by default. Outbound ACP can delegate to coding agents such as OpenCode, Claude Code, and Codex, which are optional runners rather than the dashboard itself. **Self-hosted assistant.**

## Visual workflow builders

- [Langflow](https://github.com/langflow-ai/langflow) - Visual builder for agent and retrieval flows, shipped as a Python server and as a desktop app for Windows and macOS. The README's local server listens on 127.0.0.1 port 7860, Docker is another documented start path, and a flow can be called as an API, exported as JSON, or exposed as an MCP server. The playground is for stepping through a draft while you edit it, and a durable human-approval record separate from that playground is not documented in the README. **Visual builder.**
- [n8n](https://github.com/n8n-io/n8n) - Visual automation product you can self-host with Docker or open in the hosted editor. Workflows mix integrations, JavaScript or Python, and AI steps; an agent step is one node type among general automations, and the README documents human approval inside a workflow. LICENSE.md, re-read 2026-09-30, applies the Sustainable Use License to non-.ee code for your own internal business purposes, or non-commercial or personal use, with distribution only free of charge for non-commercial purposes; files marked .ee need an n8n Enterprise license, and that Sustainable Use License is not an OSI license. **Visual automation.**
- [Activepieces](https://github.com/activepieces/activepieces) - Visual builder that assembles automations from TypeScript pieces, including AI steps and pieces that delay a run or ask a person to approve. The README describes a self-hosted deploy path and says contributed pieces can also be exposed as MCP servers. LICENSE, re-read 2026-09-30, makes content outside packages/ee and packages/server/api/src/app/ee available under MIT, while those enterprise directories have their own license; the GitHub API SPDX id was null, so this list does not call the whole repository MIT. **Visual builder.**
- [Rivet](https://github.com/Ironclad/rivet) - Desktop application for authoring prompt graphs, plus the Rivet Core TypeScript library that runs those graphs inside your own program, with prebuilt binaries listed for macOS, Linux, and Windows. Documented model and vector integrations are a fixed set, including specific OpenAI and Anthropic chat models, OpenAI embeddings, and Pinecone, rather than an open registry of existing agents. A human approval step and a durable run log are not described in the README, and the repository is not archived. **Desktop and library.**
- [Sim](https://github.com/simstudioai/sim) - Workspace for building agent workflows on a visual canvas, in conversation, or in code. The README documents a cloud app at sim.ai, a self-hosted Docker Compose install started with npx sim-setup, and a macOS desktop app that can point at that deployment, with runs, logs, and schedules viewed in the browser workspace. A human approval step is not documented in the README; optional code execution is a setup add-on that names isolated-vm, and this list did not test that boundary. **Visual builder.**
- [Dify](https://github.com/langgenius/dify) - Visual workspace for agent workflows, retrieval pipelines, and model settings, with both a cloud offer and a self-hosted Docker Compose path that opens a local install page. LICENSE, re-read 2026-09-30, is a modified Apache-2.0: operating a multi-tenant service, and removing or changing the console logo or copyright, need written authorization from the producer. The README says agents can run commands in a sandbox of their own, which this list did not test, and it documents APIs for calling Dify from your own application. **Visual platform.**

## Control planes for existing agents

- [Paperclip](https://github.com/paperclipai/paperclip) - Self-hosted Node server and React UI that coordinates agents you already run, such as Claude Code, Codex, OpenClaw, or HTTP bots, and it is a control plane for goals, roles, budgets, and tickets rather than a framework for a new model loop. The README says the default install is a local loopback service with no Paperclip account, that scheduled heartbeats wake agents, and that approval gates, pause, and budget stops are how a person intervenes. Export and import of orgs is documented with secret scrubbing, and execution workspaces can be separate git worktrees. **Self-hosted server.**
- [Symphony](https://github.com/openai/symphony) - Control plane that turns board work into implementation runs. The README says it is a low-key engineering preview for testing in trusted environments, describes a demo that watches a Linear board and spawns agents such as Codex, and uses the word isolated for those runs; this list did not test that boundary. You can implement the published spec yourself or run the experimental Elixir reference, and the README does not document a general workflow designer beyond that board-to-run loop. **Engineering preview.**
- [OpenRig](https://github.com/mvschwarz/openrig) - Multi-harness runner that boots a team of existing coding agents from a YAML spec. It overlaps the client list because it runs Claude Code and Codex, and it is not only a terminal UI: the README describes a kernel, a task queue, a shared dashboard, and a tmux TUI, needing Node 22 or 24 on macOS or Linux, with native Windows unsupported and setup writing provider hook and trust files you are told to read first. A prompt asks whether agents may run OpenRig commands without repeated permission checks, and daemon state is documented under the OpenRig home directory. **Multi-harness runner.**
- [Maestro](https://github.com/RunMaestro/Maestro) - Cross-platform desktop app that orchestrates installed coding CLIs; the README currently names Claude Code, OpenAI Codex, OpenCode, Factory Droid, and Copilot CLI in beta, and says Maestro is a pass-through so tools, skills, and logins stay with those CLIs. Auto Run sends each checklist task as a prompt in its own session instead of a live interactive turn, and git worktrees are the documented way to keep parallel agents in separate directories. A phone web view and a headless CLI are also described, and the README does not document an export format separate from the CLI session files. **Desktop app.**
- [GitHub Agentic Workflows](https://github.com/github/gh-aw) - GitHub CLI extension that compiles a Markdown file with YAML frontmatter into a GitHub Actions workflow, coordinating existing engines rather than a new model framework. Engines named in the README are GitHub Copilot, Claude Code, OpenAI Codex, Google Gemini, and Pi. The README says agent jobs are read-only and sandboxed by default and that configured writes go through separate safe-output jobs, which this list did not test; execution is on GitHub Actions after you compile, and authors are told to review permissions because runs can still go wrong. **Actions extension.**

## Maintenance, archived, and historical references

- [AutoGen](https://github.com/microsoft/autogen) - Maintenance mode: the README, re-read 2026-09-30, says AutoGen will not receive new features and points new users to Microsoft Agent Framework. The GitHub license identifier is CC-BY-4.0, not MIT. AG2 is a separate community repository, not this codebase and not a replacement for Agent Framework, while existing samples still show assistant agents and multi-agent tool use and the README limits further contributions to fixes and documentation. **Maintenance mode.**
- [Semantic Kernel](https://github.com/microsoft/semantic-kernel) - The README banner, re-read 2026-09-30, says Semantic Kernel is now Microsoft Agent Framework and directs new users there, so this row is a migration reference rather than a live framework choice. The page under that banner still documents agents, plugins, and a process model for Python, .NET, and Java. GitHub's license field for this repository is MIT, and a new project should follow the banner instead of starting here. **Maintenance SDK.**
- [Flowise](https://github.com/FlowiseAI/Flowise) - Archived reference, not a live builder, and the GitHub repository is archived. The README still describes a visual node editor you start with npm or Docker and open in a browser on local port 3000, split across server, UI, and component packages, plus a hosted cloud offer in the same document. Treat that as a snapshot of how the product was assembled, not as a current builder to adopt for new work. **Archived reference.**
- [TaskWeaver](https://github.com/microsoft/TaskWeaver) - Archived reference, not a current framework, and the GitHub repository is archived. The README describes a code-first planner and code interpreter for data analysis that keeps both chat history and in-memory Python values, such as data frames, between turns, with code execution defaulting to a container so Docker is part of the documented setup. Plugins are how you add functions for the planner to call, and those notes are historical rather than a maintained toolkit. **Archived reference.**
- [Swarm](https://github.com/openai/swarm) - Educational and historical, not a current framework. The README says Swarm is replaced by the OpenAI Agents SDK and tells readers to migrate for maintained use; the maintained libraries are the OpenAI Agents SDKs, including the JavaScript SDK named on the Agents SDK row. Swarm itself is a client-side loop of agents and handoffs over the Chat Completions API, and the README says it stores no state between calls unless you pass the earlier messages back in, so this repository is not the supported product. **Historical example.**

## Contributing

Missing something useful? Read the [contribution guide](CONTRIBUTING.md) and open an issue or pull request with an official source.

The machine-readable [list.json](list.json) includes a primary-source link and a documentation-check date for every entry. Descriptions are editorial summaries of upstream documentation; inclusion does not imply hands-on testing, a security audit, or endorsement. Hosted services and source code may have different terms.

To update the list, edit `list.json`, run `bun run build`, then `bun run check`. The README is generated; avoid editing it directly.
